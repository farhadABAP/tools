🎯 Mock Practical Tasks (Exam Format)

How the Exam Works: You will log into the SAP BTP system, open this exact dashboard, and see 3 to 4 tasks. You must build the artifacts in the system. The grading script checks if the artifacts exist, are active, and contain specific properties.

Task 1: Data Modeling & Exposure

Scenario: Create a CDS view entity named ZI_EXAM_### (replace ### with your user ID) based on the released SAP view I_BusinessPartner.

  • Expose fields: BusinessPartner, BusinessPartnerFullName, and CreationDate.
  • Make BusinessPartnerFullName searchable and a default search element.
  • Add @UI.lineItem annotations for all fields with position 10, 20, 30.
  • Set @AccessControl.authorizationCheck: #NOT_ALLOWED (since we are skipping DCL for this specific mock task, though in real exams they might ask for #CHECK).
🤖 How the Grading Script Checks This: It queries the ABAP Dictionary for an active entity named ZI_EXAM_###. It parses the source code to ensure @Search.defaultSearchElement: true is present on the exact field requested. If the view is "Inactive", you get 0 points.

Task 2: Business Logic (RAP)

Scenario: Create a Managed Behavior Definition for the entity created in Task 1.

  • Enable create and update (Disable delete).
  • Make BusinessPartner read-only.
  • Implement a determination setCreationDate that triggers on modify for create.
🤖 How the Grading Script Checks This: It checks the BDEF artifact. It looks for the exact string field ( readonly ) BusinessPartner;. It checks if the determination is mapped to the correct event (on modify { create; }). If you forgot to generate the Behavior Implementation class (BIL) and it's missing, the BDEF won't activate, resulting in 0 points.

Task 3: ABAP Class Execution (EML)

Scenario: Create an executable class ZCL_EXAM_RUN_### implementing IF_OO_ADT_CLASSRUN.

  • Use EML to create a new record in your RAP entity.
  • Commit the transaction using COMMIT ENTITIES.
  • Output the generated key or success message to the console.
🤖 How the Grading Script Checks This: It executes your class in the background. It intercepts the console output (out->write). If your EML statement fails (e.g., because you forgot IN LOCAL MODE), the class dumps or outputs nothing, and the script marks it failed.

⚠️ Grading Script Gotchas (Silent Killers)

Exam Setter Insight: 40% of candidates fail not because they don't know ABAP, but because they fall into these automated grading traps. Read these carefully.

🚨 Gotcha 1: The "IN LOCAL MODE" Trap

When you write EML (Entity Manipulation Language) inside an ABAP Class (like your ClassRun test class), you are outside the RAP transaction context. If you just write MODIFY ENTITIES..., it will fail or dump.

The Fix: You MUST append IN LOCAL MODE to your EML statements when testing in a standalone class. This bypasses the PBO/PAI feature controls for testing purposes.

MODIFY ENTITIES OF ZI_MyEntity IN LOCAL MODE
  ENTITY ZI_MyEntity
  CREATE FIELDS ( Description )
  WITH VALUE #( ( %cid = 'c1' Description = 'Test' ) )
  MAPPED DATA(lt_mapped) FAILED DATA(lt_failed) REPORTED DATA(lt_reported).

🚨 Gotcha 2: The "Activation" Cascade

In RAP, artifacts depend on each other. If you change the CDS view, the Behavior Definition might become inactive. If the BDEF is inactive, the Service Binding breaks.

The Fix: Always use "Activate All" (Ctrl+Shift+F3 in ADT) before running your test class or checking your Fiori preview. The grading script only checks active artifacts.

🚨 Gotcha 3: Ignoring the %CID (Control ID)

When creating records via EML, the grading script often checks if you mapped the temporary ID (%cid) to the actual database key.

The Fix: Always provide a %cid in your CREATE statement, and read the MAPPED table to get the real key.

🚨 Gotcha 4: Missing Access Control (DCL)

If the task says "Ensure data access is restricted based on the user's authorization", and you just put @AccessControl.authorizationCheck: #CHECK on the CDS view, you will fail.

The Fix: You must actually create a DCL (Data Control Language) artifact (.acds) that defines the WHERE clause, otherwise the CDS view will return empty data when the grader runs it.

⚡ EML & Error Handling Boilerplates

📖 EML READ with Error Catching

" Read data and capture any RAP errors
READ ENTITIES OF ZI_MyEntity IN LOCAL MODE
  ENTITY ZI_MyEntity
  ALL FIELDS WITH VALUE #( ( MyKey = '123' ) )
  RESULT DATA(lt_result)
  FAILED DATA(lt_failed)
  REPORTED DATA(lt_reported).

" How to output errors in your ClassRun
IF lt_failed IS NOT INITIAL.
  out->write( 'EML Read Failed!' ).
  out->write( lt_reported ).
  RETURN.
ENDIF.

out->write( lt_result ).

✏️ EML CREATE (The exact syntax for exams)

MODIFY ENTITIES OF ZI_MyEntity IN LOCAL MODE
  ENTITY ZI_MyEntity
  CREATE FIELDS ( Description Amount )
  WITH VALUE #( ( %cid        = 'cid1'
                  Description = 'Exam Test'
                  Amount      = 100 ) )
  MAPPED DATA(lt_mapped)
  FAILED DATA(lt_failed)
  REPORTED DATA(lt_reported).

IF lt_failed IS NOT INITIAL.
  out->write( 'Creation failed. Check validation.' ).
  out->write( lt_reported ).
  RETURN.
ENDIF.

" Commit the draft/transaction
COMMIT ENTITIES
  RESPONSE OF ZI_MyEntity
  FAILED DATA(lt_commit_failed)
  REPORTED DATA(lt_commit_reported).

out->write( 'Success! Created key:' ).
out->write( lt_mapped-myentity[ 1 ]-MyKey ).

🗄️ CDS & Access Control (DCL)

📄 CDS View with UI & Search Annotations

@AccessControl.authorizationCheck: #CHECK
@EndUserText.label: 'Exam Entity'
@Search.searchable: true
define root view entity ZI_ExamEntity
  as select from I_ReleasedTable
{
      @UI.hidden: true
  key ID,

      @Search.defaultSearchElement: true
      @UI.lineItem: [{ position: 10, label: 'Name' }]
      Name,

      @UI.lineItem: [{ position: 20, label: 'Status' }]
      Status
}

🛡️ Data Control Language (DCL) - Crucial for #CHECK

@EndUserText.label: 'Access Control for Exam Entity'
define role ZI_ExamEntity_Role {
  grant
    select on
      ZI_ExamEntity
        where
          ( Status = 'ACTIVE' ) or
          ( CreatedBy = $user );
}

🧱 RAP Behavior Definition (BDEF)

⚙️ Managed BDEF with Determination & Validation

managed implementation in class zbp_i_examentity unique;
strict ( 2 );

define behavior for ZI_ExamEntity alias Entity
persistent table zexam_db_table
draft enabled
{
  create;
  update;
  delete;

  field ( readonly ) ID;
  field ( mandatory ) Name;

  // Determination runs automatically on create
  determination setDefaultStatus on modify { create; }
  
  // Validation runs when user clicks "Save"
  validation checkName on save { create; update; }
}
