🎯 What Makes This Exam Different

This is not a multiple-choice exam. You will be given access to a real SAP BTP ABAP Environment system and a list of practical tasks to complete within 3 hours. The system auto-grades your work by checking if your artifacts (CDS views, behavior definitions, classes) exist and are syntactically correct.

🧠 Your 3-Year Experience: Double-Edged Sword

You already know ABAP. The danger is muscle memory. The exam system will reject classic ABAP statements. You must actively unlearn:

❌ Forbidden (Auto-Fail)

  • SELECT * FROM mara
  • COMMIT WORK
  • WRITE: / 'text'
  • IF sy-subrc = 0
  • CALL FUNCTION 'BAPI_...'
  • SELECTION-SCREEN
  • Direct table access to standard tables

✅ Required (Cloud Way)

  • SELECT FROM I_Material (released CDS)
  • COMMIT ENTITIES
  • out->write( 'text' )
  • TRY...CATCH cx_root
  • Released APIs only
  • Fiori Elements via annotations
  • EML for data manipulation

How System-Based Grading Works

The system checks your work automatically. It verifies:

  1. Do the required artifacts exist? (CDS view, BDEF, class, service binding)
  2. Are they syntactically correct? (No activation errors)
  3. Do they contain the required elements? (Specific fields, annotations, methods)
  4. Does the code produce the expected result when executed?
⚠️ Key Insight: Partial credit exists. If your CDS view activates but is missing one annotation, you still get points for the parts that are correct. Always activate your artifacts frequently to catch syntax errors early.

Module 1: ABAP Cloud Fundamentals STEAMPUNK

What is ABAP Cloud?

ABAP Cloud is the development model for SAP BTP ABAP Environment. It enforces a strict subset of ABAP to ensure cloud compatibility, upgrade stability, and multi-tenancy.

ABAP Cloud Extensibility Tiers NEW

The exam tests your understanding of the three-tier extensibility model:

  • Tier 1 (Cloud-Compliant): Uses only released SAP APIs and CDS views. Full cloud compatibility. This is what you develop in the exam.
  • Tier 2 (Cloud-Ready): Uses some non-released but stable APIs. May break during upgrades.
  • Tier 3 (Classic): Full ABAP access. Not cloud-compatible. Not available in BTP ABAP Environment.

Released Objects (Whitelist)

Only SAP objects marked as "released" can be used in Tier 1. Check via:

  • Eclipse ADT: Project Explorer → Released Objects
  • SAP BAS: Released Objects app
  • Look for the annotation @EndUserText.label on released CDS views

Modern ABAP Syntax (Mandatory in Cloud)

" Inline declarations
DATA(lv_count) = 0.
DATA(ls_struct) = VALUE #( field1 = 'A' field2 = 'B' ).

" Constructor expressions
DATA(lt_data) = VALUE tt_type( ( id = 1 ) ( id = 2 ) ).

" String templates
DATA(lv_msg) = |User { sy-uname } logged in at { sy-uzeit TIME = ISO }|.

" Modern loops
LOOP AT lt_data INTO DATA(ls_item) WHERE status = 'A'.
  " ...
ENDLOOP.

" FOR expressions (inline iteration)
DATA(lt_names) = VALUE string_table(
  FOR ls IN lt_data ( ls-name ) ).

" Conditional expressions
DATA(lv_status) = COND #( WHEN lv_count > 0 THEN 'OK' ELSE 'EMPTY' ).

Module 2: ABAP Object-Oriented CLEAN CODE

Executable Classes (IF_OO_ADT_CLASSRUN)

Replaces REPORT and START-OF-SELECTION. This is how you test code in ABAP Cloud.

CLASS zcl_my_test DEFINITION PUBLIC FINAL CREATE PUBLIC.
  PUBLIC SECTION.
    INTERFACES if_oo_adt_classrun.
ENDCLASS.

CLASS zcl_my_test IMPLEMENTATION.
  METHOD if_oo_adt_classrun~main.
    TRY.
        DATA(lo_processor) = NEW zcl_processor( ).
        lo_processor->execute( ).
        out->write( 'Success' ).
      CATCH cx_root INTO DATA(lx_error).
        out->write( lx_error->get_text( ) ).
    ENDTRY.
  ENDMETHOD.
ENDCLASS.

Exception Handling (No SY-SUBRC)

METHOD process_data.
  TRY.
      DATA(lv_result) = calculate( iv_input ).
    CATCH cx_sy_arithmetic_error INTO DATA(lx_arith).
      " Handle specific exception
      RAISE EXCEPTION TYPE zcx_custom_error
        EXPORTING previous = lx_arith.
    CATCH cx_root INTO DATA(lx_general).
      " Catch-all fallback
      out->write( lx_general->get_text( ) ).
  ENDTRY.
ENDMETHOD.

Constructor Injection Pattern NEW

CLASS zcl_service DEFINITION PUBLIC FINAL CREATE PUBLIC.
  PUBLIC SECTION.
    METHODS constructor IMPORTING io_repo TYPE REF TO zif_repository.
    METHODS get_data RETURNING VALUE(rt_data) TYPE tt_data.
  PRIVATE SECTION.
    DATA mo_repo TYPE REF TO zif_repository.
ENDCLASS.

CLASS zcl_service IMPLEMENTATION.
  METHOD constructor.
    mo_repo = io_repo. " Dependency injected, not CREATE OBJECT
  ENDMETHOD.
  METHOD get_data.
    rt_data = mo_repo->read_all( ).
  ENDMETHOD.
ENDCLASS.

Module 3: CDS View Engineering FOUNDATION

CDS View Entity with Full Annotations

@AccessControl.authorizationCheck: #CHECK
@EndUserText.label: 'Billing Document'
@Search.searchable: true
@Metadata.allowExtensions: true
define root view entity ZI_BillingDoc
  as select from I_BillingDocument
  association [0..1] to I_CompanyCode as _CompanyCode
    on $projection.CompanyCode = _CompanyCode.CompanyCode
{
      @UI.hidden: true
  key BillingDocument,

      @Search.defaultSearchElement: true
      @UI.lineItem: [{ position: 10, label: 'Company' }]
      @Consumption.valueHelpDefinition: [{ entity: { name: 'I_CompanyCode', element: 'CompanyCode' } }]
      CompanyCode,

      @UI.lineItem: [{ position: 20, label: 'Customer' }]
      @Search.defaultSearchElement: true
      CustomerName,

      @UI.lineItem: [{ position: 30, label: 'Net Amount' }]
      @Semantics.amount.currencyCode: 'Currency'
      TotalNetAmount,

      @UI.lineItem: [{ position: 40 }]
      @Semantics.currencyCode: true
      TransactionCurrency,

      " Path expression via association
      _CompanyCode.CompanyName as CompanyNameText
}

CDS Access Control (DCL) NEW

When you use @AccessControl.authorizationCheck: #CHECK, you MUST create a DCL (Data Control Language) source:

@EndUserText.label: 'Access control for ZI_BillingDoc'
define role ZI_BillingDoc_Access {
  grant select on ZI_BillingDoc
    where ( CompanyCode ) = aspect pfcg_auth( F_BKPF_BUK, BUKRS );
}

Module 4: RAP (RESTful ABAP Programming) CORE

RAP Architecture Overview

  1. Data Model: CDS Interface View → CDS Consumption (Projection) View
  2. Behavior: Behavior Definition (BDEF) → Behavior Implementation (BIL class)
  3. Service: Service Definition → Service Binding (OData V2/V4)

Behavior Definition (BDEF) — Full Syntax

managed implementation in class zbp_i_billingdoc unique;
strict ( 2 );

define behavior for ZI_BillingDoc alias Billing
  persistent table zbillingdoc
  draft enabled
  lock master
  authorization master ( instance )
  etag master LastChangedAt
{
  create;
  update;
  delete;

  field ( readonly ) BillingDocument;
  field ( mandatory ) CustomerName;
  field ( numbering : managed ) BillingDocument;

  " Early numbering: framework assigns key before save
  " numbering : managed = framework generates key

  determination setDefaults on modify { create; }
  validation validateCustomer on save { create; update; }

  action ( features : instance ) approve result [1] $self;

  draft action Edit;
  draft action Activate;
  draft action Discard;
  draft action Resume;
  draft action Prepare;
}

Behavior Implementation Class (BIL) EXAM CRITICAL

You WILL have to write this in the exam. This is the actual ABAP class behind the BDEF:

CLASS lhc_Billing DEFINITION INHERITING FROM cl_abap_behavior_handler.
  PRIVATE SECTION.
    METHODS get_instance_authorizations FOR INSTANCE AUTHORIZATION
      IMPORTING keys REQUEST requested_authorizations FOR Billing RESULT result.

    METHODS setDefaults FOR DETERMINE ON MODIFY
      IMPORTING keys FOR Billing~setDefaults.

    METHODS validateCustomer FOR VALIDATE ON SAVE
      IMPORTING keys FOR Billing~validateCustomer.
ENDCLASS.

CLASS lhc_Billing IMPLEMENTATION.

  METHOD get_instance_authorizations.
    " Implement authorization checks here
  ENDMETHOD.

  METHOD setDefaults.
    READ ENTITIES OF ZI_BillingDoc IN LOCAL MODE
      ENTITY Billing
        FIELDS ( CustomerName )
        WITH CORRESPONDING #( keys )
      ASSIGNING FIELD-SYMBOL(<lt_data>).

    MODIFY ENTITIES OF ZI_BillingDoc IN LOCAL MODE
      ENTITY Billing
        UPDATE FIELDS ( TransactionCurrency )
        WITH VALUE #( FOR ls IN <lt_data> (
          %tky = ls-%tky
          TransactionCurrency = 'EUR' ) ).
  ENDMETHOD.

  METHOD validateCustomer.
    READ ENTITIES OF ZI_BillingDoc IN LOCAL MODE
      ENTITY Billing
        FIELDS ( CustomerName )
        WITH CORRESPONDING #( keys )
      RESULT DATA(lt_data).

    LOOP AT lt_data INTO DATA(ls_data).
      IF ls_data-CustomerName IS INITIAL.
        APPEND VALUE #( %tky = ls_data-%tky ) TO failed-billing.
        APPEND VALUE #( %tky = ls_data-%tky
                        %msg = new_message( id = 'ZMSG' number = '001'
                                            severity = if_abap_behv_message=>severity-error )
                      ) TO reported-billing.
      ENDIF.
    ENDLOOP.
  ENDMETHOD.

ENDCLASS.

EML — All Operations EXAM CRITICAL

" ===== READ =====
READ ENTITIES OF ZI_BillingDoc IN LOCAL MODE
  ENTITY Billing
    FIELDS ( CustomerName TotalNetAmount )
    WITH VALUE #( ( BillingDocument = '0001' ) )
  RESULT DATA(lt_result)
  FAILED DATA(lt_failed)
  REPORTED DATA(lt_reported).

" ===== CREATE =====
MODIFY ENTITIES OF ZI_BillingDoc IN LOCAL MODE
  ENTITY Billing
    CREATE FIELDS ( CustomerName TotalNetAmount TransactionCurrency )
    WITH VALUE #( ( %cid = 'ref1'
                    CustomerName = 'Test Customer'
                    TotalNetAmount = '1000'
                    TransactionCurrency = 'EUR' ) )
  MAPPED DATA(lt_mapped)
  FAILED DATA(lt_create_failed)
  REPORTED DATA(lt_create_reported).

" ===== UPDATE =====
MODIFY ENTITIES OF ZI_BillingDoc IN LOCAL MODE
  ENTITY Billing
    UPDATE FIELDS ( CustomerName )
    WITH VALUE #( ( BillingDocument = '0001'
                    CustomerName = 'Updated Name'
                    %control-CustomerName = if_abap_behv=>mk-on ) )
  FAILED DATA(lt_upd_failed)
  REPORTED DATA(lt_upd_reported).

" ===== DELETE =====
MODIFY ENTITIES OF ZI_BillingDoc IN LOCAL MODE
  ENTITY Billing
    DELETE FROM VALUE #( ( BillingDocument = '0001' ) )
  FAILED DATA(lt_del_failed)
  REPORTED DATA(lt_del_reported).

" ===== COMMIT (always after MODIFY in standalone classes) =====
COMMIT ENTITIES
  RESPONSE OF ZI_BillingDoc
  FAILED DATA(lt_commit_failed)
  REPORTED DATA(lt_commit_reported).
💡 %control explained: The %control structure tells the framework WHICH fields you intend to update. %control-CustomerName = if_abap_behv=>mk-on means "I am intentionally setting this field." Without it, the framework may ignore your update.
💡 IN LOCAL MODE explained: Use IN LOCAL MODE when calling EML from within a behavior implementation or a class that is NOT part of the RAP transactional flow. It bypasses authorization checks and feature controls. In the exam, you will almost always need this.

Module 5: Service Exposure NEW

Service Definition

Exposes your CDS projection view as a service. This is the bridge between your data model and the OData protocol.

@EndUserText.label: 'Billing Document Service'
define service ZUI_BillingDoc {
  expose ZC_BillingDoc as BillingDocument;
}

Behavior Projection

Projects the behavior from the interface view to the consumption view:

projection;
strict ( 2 );

define behavior for ZC_BillingDoc alias BillingDocument {
  use create;
  use update;
  use delete;

  use action Edit;
  use action Activate;
  use action Discard;
  use action Resume;
  use action Prepare;
  use action approve;
}

Service Binding

Created via the Eclipse ADT wizard or BAS. You select the Service Definition and choose the binding type:

  • OData V2 - UI: For SAP Fiori Elements apps (most common in exam)
  • OData V4 - UI: Newer protocol, also valid
  • OData V4 - Web API: For programmatic consumption
⚠️ Exam Tip: After creating the Service Binding, you must publish it (click the "Publish" button). An unpublished binding will not expose the OData service, and the auto-grader may mark the task as failed.

Complete RAP Artifact Chain

" 1. Interface CDS View (data model)
define root view entity ZI_BillingDoc as select from ...

" 2. Behavior Definition (business logic contract)
define behavior for ZI_BillingDoc ...

" 3. Behavior Implementation (ABAP class with actual logic)
CLASS lhc_Billing DEFINITION INHERITING FROM cl_abap_behavior_handler ...

" 4. Projection CDS View (consumption layer)
define root view entity ZC_BillingDoc as projection on ZI_BillingDoc ...

" 5. Behavior Projection
projection;
define behavior for ZC_BillingDoc ...

" 6. Service Definition
define service ZUI_BillingDoc { expose ZC_BillingDoc as BillingDocument; }

" 7. Service Binding (created via wizard, published manually)

Module 6: Joule & AI-Augmented Dev EXAM TESTED

What the Exam Tests About Joule

The exam description explicitly states it "validates your proficiency in leveraging Joule for developers." This means:

  • You must know how to open Joule in BAS/ADT
  • You must write effective prompts that produce usable code
  • You must be able to review and correct Joule's output
  • You must use Joule for code generation, explanation, and optimization

Joule Prompting Best Practices

  • Be specific: "Create a managed RAP behavior definition for ZI_Flight with draft enabled" beats "Write RAP code"
  • Include constraints: Mention "ABAP Cloud compliant", "use released APIs only"
  • Specify output format: "Include TRY...CATCH exception handling" or "Use inline declarations"
  • Iterate: If Joule's first output is wrong, say "Fix the syntax error on line 12" rather than starting over
💡 Exam Strategy: Use Joule to generate the heavy boilerplate (BDEF, BIL skeleton, CDS annotations), then spend YOUR time on the business logic (validation rules, determination logic, EML calls). This is the time-management key to passing.

🧱 BIL: Determination + Validation

CLASS lhc_Entity DEFINITION INHERITING FROM cl_abap_behavior_handler.
  PRIVATE SECTION.
    METHODS setDefaults FOR DETERMINE ON MODIFY
      IMPORTING keys FOR Entity~setDefaults.
    METHODS validateData FOR VALIDATE ON SAVE
      IMPORTING keys FOR Entity~validateData.
ENDCLASS.

CLASS lhc_Entity IMPLEMENTATION.
  METHOD setDefaults.
    MODIFY ENTITIES OF ZI_MyEntity IN LOCAL MODE
      ENTITY Entity
        UPDATE FIELDS ( Currency )
        WITH VALUE #( FOR key IN keys (
          %tky = key-%tky
          Currency = 'EUR' ) ).
  ENDMETHOD.

  METHOD validateData.
    READ ENTITIES OF ZI_MyEntity IN LOCAL MODE
      ENTITY Entity
        FIELDS ( Description )
        WITH CORRESPONDING #( keys )
      RESULT DATA(lt_data).

    LOOP AT lt_data INTO DATA(ls).
      IF ls-Description IS INITIAL.
        APPEND VALUE #( %tky = ls-%tky ) TO failed-entity.
        APPEND VALUE #( %tky = ls-%tky
          %msg = new_message( id = 'ZMSG' number = '001'
            severity = if_abap_behv_message=>severity-error )
        ) TO reported-entity.
      ENDIF.
    ENDLOOP.
  ENDMETHOD.
ENDCLASS.
